# Skills 用户交互与测试流程

日期：2026-04-30

状态：MVP 交互与验收口径

## 文档目的

这份文档给完全不了解 DeerFlow 内部实现的小伙伴使用。

读完后，他应该能做三件事：

1. 扮演普通 Agent 使用者，在系统里完成 Skills 的核心交互。
2. 按步骤测试“安装 Skill、绑定 Agent、对话中生效、手动更新”这条 MVP 主流程。
3. 判断流程只是页面显示成功，还是 Agent 真的调用到了当前用户安装的 Skill 本体。

这份文档不是接口测试计划，也不是领域模型说明。它只回答：

1. 用户在页面上应该怎么走。
2. 页面应该让用户看到什么。
3. 测试同学怎么判断这条链路真的跑通。
4. 功能还没实现时，产品、设计、前端、后端应该围绕哪些交互点继续讨论。

## 用户角色

MVP 主角是普通 Agent 使用者。

他只想给自己的 Agent 增加能力，不关心 Skill 是怎么存储、怎么挂载、怎么加载的。

他应该理解的事情只有：

1. SkillHub 里有别人或官方提供的 Skill。
2. 我可以把 Skill 安装到自己的空间。
3. 我可以把已安装 Skill 绑定给某个 Agent。
4. Agent 之后对话时应该能使用这个 Skill。
5. Skill 有新版时，只有我手动更新后，Agent 才会使用新版。

上传、发布、复杂版本策略不是这份 MVP 流程的主角。上传可以作为测试数据准备手段，但普通用户主流程优先验证“安装”。

## 页面不能要求用户理解的词

普通用户不应该被要求理解这些概念：

1. `SKILL.md`
2. frontmatter
3. package version
4. public latest
5. artifact
6. Runtime Manifest
7. sandbox allowlist
8. OSS 路径
9. 用户目录或 public 目录
10. 文件路径映射

如果页面或测试步骤必须解释这些词，说明交互还没有收敛到普通用户能理解的程度。

## 用户可见概念

| 用户看到的词 | 用户应该怎么理解 |
| --- | --- |
| SkillHub | 可以发现和安装 Skill 的地方 |
| 我的 Skills | 我已经拥有、安装或创建的 Skill |
| 已安装 | 这个 Skill 已经进入我的空间，可以绑定给 Agent |
| Agent Skills | 当前 Agent 使用的 Skills |
| 版本 1、版本 2、版本 3 | 平台替用户维护的内容版本 |
| 更新 | 有新版可选，但不会自动改变 Agent |

版本号由平台维护。Skill 包里有没有版本信息，都不应该影响用户看到的“版本 1、版本 2、版本 3”。

## MVP 主流程

MVP 只需要先跑通这一条主线：

```text
打开 SkillHub
-> 安装一个 Skill
-> 在我的 Skills 里看到它
-> 把它绑定给 Agent
-> 和 Agent 对话
-> 验证 Agent 真的使用了这个 Skill
-> Skill 有新版时手动更新
-> 再次验证 Agent 使用新版
```

【关键点】安装成功不等于验收成功。只有 Agent 对话中真的表现出这个 Skill 的行为，才算主流程完成。

## 测试准备：运行验收 Skill

为了让不了解内部实现的人也能判断 Agent 是否真的调用到 Skill，MVP 测试环境需要准备一个“运行验收 Skill”。

这个 Skill 不需要暴露内部路径，也不需要用户填写版本。平台只展示版本 1 和版本 2。

建议测试数据：

| 平台版本 | Skill 行为 |
| --- | --- |
| 版本 1 | 当用户说“请执行 Skill 运行验收”时，Agent 回复 `SKILL_RUNTIME_OK_V1` |
| 版本 2 | 当用户说“请执行 Skill 运行验收”时，Agent 回复 `SKILL_RUNTIME_OK_V2` |

这个 Skill 的作用不是展示真实业务能力，而是验证运行链路：

1. 用户安装的是哪个版本。
2. Agent 绑定的是用户空间里的已安装 Skill。
3. Agent 运行时读取的是绑定版本的 Skill 本体。
4. 发布新版后，未手动更新的 Agent 仍使用旧版。
5. 手动更新后，Agent 下一次运行才使用新版。

如果当前功能还没有实现，可以先用这份测试数据作为产品和研发对齐的交互目标。

## 流程一：从 SkillHub 安装 Skill

### 任务

用户打开 SkillHub，找到“运行验收 Skill”，安装到自己的空间。

### 期望交互

1. SkillHub 列表能看到 Skill 名称、描述、来源、当前版本和安装状态。
2. 未安装时，主按钮是“安装”。
3. 点击安装后，页面显示安装中状态。
4. 安装成功后，状态变成“已安装”。
5. 成功态提供两个自然下一步：
   - 查看我的 Skills。
   - 绑定到 Agent。

### 通过信号

1. 用户不用理解 Skill 包结构，也能完成安装。
2. 用户知道这个 Skill 现在属于“我的空间”。
3. 我的 Skills 中能看到这个 Skill。
4. 我的 Skills 中展示当前版本为“版本 1”。

### 失败信号

1. 用户看到的是“Download”而不是“安装”。
2. 页面要求用户填写或确认包内版本。
3. 安装成功后用户不知道下一步去哪里。
4. SkillHub 显示已安装，但我的 Skills 找不到它。

## 流程二：把已安装 Skill 绑定给 Agent

### 任务

用户进入某个 Agent 的配置页，把“运行验收 Skill”绑定给这个 Agent。

### 期望交互

1. Agent 配置页有清楚的 Skills 区域。
2. 添加 Skill 时，只展示当前用户可绑定的 Skills。
3. Skill 选项展示名称、来源和当前版本。
4. 用户选择“运行验收 Skill”并保存。
5. 保存后，Agent Skills 区域能看到已绑定 Skill 和版本 1。

### 通过信号

1. 用户能从已安装 Skills 中选择 Skill。
2. 用户能确认这个 Agent 当前启用了哪些 Skills。
3. 用户能看到当前绑定版本，不需要理解内部 ID 或路径。

### 失败信号

1. Agent 配置页只能按名字选择，看不出来源和版本。
2. 用户误以为在 SkillHub 里点安装就已经自动绑定 Agent。
3. 保存成功后，Agent 页面看不到已启用 Skills。
4. 同名 Skill 出现时，用户无法判断自己绑定的是哪一个。

## 流程三：在对话中验证 Skill 生效

### 任务

用户打开刚才的 Agent，发起一次新对话，输入：

```text
请执行 Skill 运行验收
```

### 期望结果

Agent 回复：

```text
SKILL_RUNTIME_OK_V1
```

### 通过信号

1. Agent 回复版本 1 的验收文本。
2. 对话页能看到当前 Agent 启用了 Skills，至少能看到 Skill 名称。
3. 如果支持展开详情，用户能看到这个 Skill 当前是版本 1。

### 失败信号

1. Agent 泛泛回答，没有触发验收 Skill。
2. Agent 回复了版本 2 的验收文本，说明它可能读到了最新版而不是用户安装版本。
3. Agent 回复另一个同名 Skill 的行为。
4. 页面显示已绑定，但运行时提示找不到 Skill。
5. 运行时失败后，Agent 静默改用默认能力继续回答。

【关键点】第 5 点不能接受。Skill 不可用时，系统应该明确告诉用户这个 Agent 的某个 Skill 当前不可用，而不是静默回退。

## 流程四：发布新版后，未更新用户仍使用旧版

### 任务

测试环境准备“运行验收 Skill”的版本 2。用户不点击更新，直接再次使用 Agent 对话。

### 期望交互

1. SkillHub 或我的 Skills 能提示“有更新”。
2. 用户能看到当前已安装版本是版本 1，可更新版本是版本 2。
3. 用户没有点击更新前，Agent 绑定状态仍显示版本 1。

### 期望结果

用户再次输入：

```text
请执行 Skill 运行验收
```

Agent 仍回复：

```text
SKILL_RUNTIME_OK_V1
```

### 通过信号

1. 发布新版不会自动改变用户 Agent。
2. 用户未确认更新前，Agent 仍使用版本 1。
3. 页面不会用“最新版”这种模糊说法掩盖当前实际使用版本。

### 失败信号

1. 新版发布后，Agent 自动回复 `SKILL_RUNTIME_OK_V2`。
2. 页面只显示“已安装”，但看不到当前安装版本。
3. 用户不知道不更新是否还能继续使用旧版。

## 流程五：用户手动更新后，Agent 使用新版

### 任务

用户在我的 Skills 或更新提示中点击更新，把已安装 Skill 从版本 1 更新到版本 2。

### 期望交互

更新确认页至少展示：

1. 当前版本：版本 1。
2. 可更新版本：版本 2。
3. 更新说明。
4. 受影响 Agent 列表。
5. 主操作：“更新”。
6. 次操作：“暂不更新”。

### 期望结果

用户确认更新后，重新打开 Agent 或发起新对话，输入：

```text
请执行 Skill 运行验收
```

Agent 回复：

```text
SKILL_RUNTIME_OK_V2
```

### 通过信号

1. 用户确认更新前知道会影响哪些 Agent。
2. 确认更新后，我的 Skills 显示当前版本 2。
3. Agent Skills 区域显示当前版本 2。
4. 新对话中 Agent 回复版本 2 的验收文本。

### 失败信号

1. 更新确认页没有受影响 Agent 列表。
2. 更新后页面显示版本 2，但 Agent 仍回复版本 1。
3. 更新后 Agent 回复泛泛内容，说明 Skill 没有被运行时加载。
4. 更新动作覆盖了错误的同名 Skill。

## 流程六：Skill 运行不可用时要明确失败

### 任务

当一个 Skill 已经安装并绑定，但运行时无法读取它的 Skill 本体时，系统要给用户明确反馈。

这个场景可以由研发或测试同学在测试环境中模拟。普通用户不需要知道失败原因是路径映射、artifact 缺失还是运行授权失败。

### 期望交互

1. Agent 配置页能提示某个已绑定 Skill 当前不可用。
2. 对话页触发该 Skill 时，明确提示 Skill 不可用。
3. 提示内容告诉用户可以去 Agent 配置或 Skills 页面处理。
4. 系统不能偷偷改用同名 Skill、公共最新版或默认能力。

### 通过信号

1. 用户能看懂“这个 Skill 当前不可用”。
2. 测试同学能确认系统没有静默回退。
3. 研发同学能从日志或运行记录中定位是哪个 Skill 版本解析失败。

### 失败信号

1. UI 全部显示正常，但 Agent 实际没用到 Skill。
2. 运行失败后，Agent 继续给出看似正常的答案。
3. 系统回退到 SkillHub 最新版。
4. 系统回退到同名目录或同名 Skill。

## 核心验收矩阵

| 阶段 | 用户看到 | 必须验证 |
| --- | --- | --- |
| 安装 | SkillHub 中状态变成已安装 | 我的 Skills 中出现该 Skill，版本为平台版本 1 |
| 绑定 | Agent Skills 中出现该 Skill | Agent 绑定的是用户已安装 Skill，不是 SkillHub 公共对象 |
| 运行 | Agent 回复 `SKILL_RUNTIME_OK_V1` | Agent 运行时读取的是版本 1 的 Skill 本体 |
| 新版发布 | 页面提示有更新 | 未确认更新前，Agent 仍使用版本 1 |
| 手动更新 | 当前版本变成版本 2 | Agent 下一次运行读取版本 2 的 Skill 本体 |
| 运行失败 | 用户看到 Skill 不可用 | 系统不静默回退到 public latest、同名目录或默认能力 |

## 交互设计待确认点

这些点决定 MVP 是否足够顺：

1. 安装成功后，是直接给“绑定到 Agent”按钮，还是先进入我的 Skills。
2. Agent 配置页的 Skills 区域展示多少信息：名称、来源、版本、更新状态至少要有。
3. 对话页是否展示当前启用 Skills 数量，以及是否允许展开查看名称和版本。
4. 更新提示放在 SkillHub、我的 Skills、Agent 配置页，还是三处都要有。
5. Skill 不可用时，错误提示在 Agent 配置页出现，还是在对话触发时出现，还是两处都出现。
6. 同名 Skill 在选择和绑定时如何展示来源，避免用户选错。

## 不进入 MVP 主流程

第一版主流程不验证这些能力：

1. 用户手写版本号。
2. Skill 包内版本作为平台版本。
3. 自动更新。
4. 复杂 diff。
5. 回滚。
6. 单个 Agent 固定到某个历史版本。
7. 评分评论。
8. 付费市场。
9. 多人协作编辑。
10. 自动合并用户基于别人 Skill 修改后的内容。

这些可以作为后续能力记录，但不能阻塞“安装、绑定、运行、手动更新”主流程。

## 失败分级

| 等级 | 含义 | 示例 |
| --- | --- | --- |
| P0 | 主链路不可用或运行时错误被静默掩盖 | 页面显示已绑定，但 Agent 没有调用 Skill；Agent 回退到公共最新版 |
| P1 | 用户可以完成，但关键状态不清楚 | 用户不知道当前 Agent 用的是版本 1 还是版本 2 |
| P2 | 文案或布局影响效率，但不阻塞理解 | 安装成功后的下一步入口不够明显 |

P0 必须优先修。对这个 MVP 来说，最严重的问题不是用户点错按钮，而是页面流程看起来成功，Agent 实际没有读取用户安装的 Skill 本体。
