# Product Contract

日期：2026-04-29

状态：产品口径

## 文档目的

这份文档只定义普通用户视角下的 Skills 产品契约。它不描述接口，不讨论迁移步骤，不列测试用例。

读完后应该能判断：一个 Skills 相关需求是否符合我们要做的 SkillHub 与平台版本模型。

## 目标用户

目标用户是普通使用者。他们不理解 Agent 开发内幕，也不应该理解系统如何加载 skill、如何解析文件、如何拼接上下文、如何选择工具。

用户只需要理解：

1. 我可以给 Agent 增加某种能力。
2. 我可以从社区空间下载别人或官方做好的能力到我的空间。
3. 我可以上传、创建或 fork 自己的能力。
4. 我可以把能力绑定到某个 Agent。
5. 我可以发布、更新、安装新版，但这些动作必须由我明确确认。

## Skill 是什么

面向用户时，Skill 是一种可复用的 Agent 能力包。

用户不需要看到“包结构”“frontmatter”“运行时注入”“工具权限”等内部概念。页面应该使用更直观的词：

| 内部概念 | 用户侧表达 |
| --- | --- |
| skill package | Skill / 能力 |
| custom skill | 我的 Skill |
| public skill | 社区空间中的 Skill |
| official skill | 官方 Skill |
| community skill | 社区 Skill |
| skill version | 版本 |
| release notes | 更新说明 |
| install/download | 下载到我的空间 / 添加到我的空间 |
| fork/remix | 基于此创建我的版本 |

## 版本由平台管理

版本代表 Skill 内容版本，由平台生成、保存和展示。用户不能在 Skill 内容里随意写版本号来影响平台版本。

产品规则：

1. 平台每次接受一次有效内容变更，都生成一个不可变的 Skill 版本。
2. 用户可以填写更新说明，但不能手写平台版本号。
3. 导入包里如果存在自带版本字段，只能作为兼容信息或导入来源备注，不能作为平台版本来源。
4. 发布到 SkillHub 的版本必须来自平台已生成的内容快照。
5. 已安装用户不会因为发布者发布新版本而被自动影响。

推荐展示：

1. 普通用户看到“版本 1”“版本 2”“版本 3”。
2. 更新记录中展示发布时间、发布者、更新说明。
3. 内部唯一 ID、内容哈希、导入来源版本等信息不作为普通用户主界面内容。

## 两个用户空间

Skills 产品首先是两个空间：

1. 社区空间：负责发现和下载 Skill。
2. 我的空间：负责管理我能给 Agent 使用的 Skill。

社区空间里有两类 Skill：

1. 官方 Skill：来自系统预置来源。旧 `public` 目录下的 Skill 在用户侧应视为官方 Skill，作者显示为 official/官方。
2. 社区 Skill：用户上传或创建后发布出来，其他用户可以下载。

社区空间后续必须支持搜索和筛选，至少包括：

1. 按 Skill 名称搜索。
2. 按作者搜索或筛选。

因此作者、来源和 Skill 名称必须是用户侧一等信息，不能只藏在内部 ID 或调试字段里。

我的空间里也有两类 Skill：

1. 我下载的 Skill：从社区空间下载进来，可以绑定 Agent，可以手动更新，但我不是原作者。
2. 我的 Skill：我上传、创建或 fork 得到的 Skill，可以迭代、绑定 Agent、发布到社区空间。

“下载”在产品语义里不是让用户理解文件复制，而是“把社区空间里的 Skill 添加到我的空间，使它可以被我的 Agent 选择和使用”。

## 核心概念

必须区分官方 Skill、社区 Skill、我的 Skill、已安装 Skill。

| 概念 | 用户看到的位置 | 谁维护 | 用户能做什么 |
| --- | --- | --- | --- |
| 官方 Skill | 社区空间 | 平台 | 下载到我的空间、查看、基于此创建 |
| 社区 Skill | 社区空间 | 发布者 | 下载到我的空间、查看、基于此创建、更新已下载版本 |
| 我下载的 Skill | 我的空间 / Agent 绑定页 | 原作者维护源版本，当前用户维护自己的下载版本选择 | 绑定到 Agent、查看当前版本、手动更新、fork 成我的 Skill |
| 我的 Skill | 我的空间 | 当前用户 | 上传、创建、fork、迭代、绑定、发布、删除未发布内容 |
| 已发布 Skill | 社区空间 | 当前发布者 | 被其他用户下载；发布者可管理发布版本 |

Agent 绑定的不是社区空间里的公共对象，而是用户自己空间里的 Skill。这个 Skill 可能是我下载的，也可能是我的 Skill。

这个契约保证：

1. SkillHub 发布新版本时，不会偷偷改变用户 Agent 的行为。
2. 用户 B 安装了用户 A 的版本 1 后，即使用户 A 发布版本 2，用户 B 仍然停留在版本 1。
3. 用户 B 只有点击更新并确认后，自己的 Agent 才开始使用新版本。

## Skill 身份与版本身份

需要区分：

1. Skill 身份：这是哪个 Skill。
2. 版本身份：这是该 Skill 的哪一次内容快照。
3. 安装身份：某个用户安装了哪个 Skill 的哪个版本。
4. 绑定身份：某个 Agent 使用该用户空间里的哪个已安装 Skill。

用户看起来是简单的“安装并使用”，但底层必须有这些边界，否则更新、回滚和发布都会混乱。

## SkillHub 中的公共不等于系统预制

社区空间中至少有两种来源：

1. 官方：平台维护，默认推荐，可信度更高。
2. 社区：用户发布，其他用户可安装。

如果“public skill”同时承担官方预制和社区发布两种语义，用户会困惑：

1. 这个 Skill 是平台提供的，还是某个用户上传的？
2. 我安装后能不能改？
3. 我发布新版会不会覆盖官方版本？
4. 我安装的是官方版还是社区版？

## Fork 与发布治理

用户可以基于官方或社区 Skill 创建自己的版本。这个动作在用户侧叫“基于此创建我的版本”或 fork。

产品规则：

1. fork 会在我的空间创建一个新的“我的 Skill”。
2. fork 后的 Skill 必须保留来源归因，至少让用户知道它基于哪个官方或社区 Skill。
3. fork 不会修改原 Skill，也不会自动发布到社区空间。
4. 发布 fork 时，系统必须防止用户把未修改或近似未修改的 Skill 当成自己的原创 Skill 发布。
5. 本版本先 hard-block 未修改 fork 发布；实现上按来源版本的文件/内容 hash 做精确相等拦截。
6. 后续发布流程会引入审核机制；复杂相似度、人工审核、版权/许可证治理放到后续扩展。

## 必须坚持的非目标

第一版不要做：

1. 用户自定义 SemVer。
2. 自动更新。
3. 复杂依赖版本矩阵。
4. 付费市场。
5. 评分评论。
6. 多人协作编辑。
7. 自动合并用户魔改版本。

这些能力不是不重要，而是会在主链路跑通前制造过多复杂度。
