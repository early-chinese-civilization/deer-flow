# Boundary Rules

日期：2026-04-29

状态：边界规则

## 文档目的

这份文档只收敛边界情况和产品规则。它不描述主流程细节，不讨论当前代码差距。

读完后应该能在上传、绑定、发布、安装、更新、删除、禁用等场景下做出一致判断。

## 版本规则

平台版本号从 1 开始递增，普通用户看到“版本 1”“版本 2”“版本 3”。

每个版本都是不可变内容快照：

1. 版本 1 创建后，不能原地修改版本 1 的内容。
2. 修改内容必须创建版本 2。
3. 已发布版本不能被偷偷替换。
4. 安装了版本 1 的用户永远可以确认自己安装的是版本 1。

导入包自带版本的处理：

1. 上传时不要求用户在 Skill 内容里写版本号。
2. 上传包里有自带版本字段时，平台不把它当成平台版本号。
3. 平台可以后台记录“导入来源版本”，用于排查问题。
4. 普通用户主界面只展示平台版本。
5. 未来导出 Skill 时，也不要求用户靠手写版本号管理平台版本。

同内容重复上传：

1. 不创建新版本。
2. 提示“内容未变化，已保留当前版本”。
3. 如果用户只是想重新安装，可以后续提供高级操作，不作为主路径。

## 上传边界

必须拒绝：

1. 没有 Skill 说明文件。
2. 有多个根 Skill，平台无法判断用户要上传哪一个。
3. 压缩包路径包含危险路径。
4. 文件过大。
5. 文件数量过多。
6. 包含暂不支持的可执行内容。
7. 描述为空或名称为空。

拒绝后不创建 Skill，不创建版本，不留下用户可见文件。

如果上传中断或解析失败：

1. 用户空间不出现半成品。
2. 再次上传同一文件可以正常重试。
3. 临时文件由后台清理，不让用户处理。

第一版建议只支持一次上传一个 Skill。未来支持多 Skill 批量上传时，需要逐个返回结果。

## 同名冲突

SkillHub 中允许不同作者有同名或相近名称，但必须通过作者、来源和唯一页面区分。

我的空间中不建议允许两个同名 Skill 并列存在。

推荐规则：

1. 我的空间同名冲突时，提示用户“更新已有 Skill”或“另存为新 Skill”。
2. 另存为新 Skill 时，平台建议一个新名称。
3. 社区 Skill 不能覆盖官方 Skill 的身份。
4. 用户基于官方 Skill 创建自己的版本时，默认名称加上“副本”或允许用户重命名。

## Agent 绑定边界

推荐第一版规则：

1. Agent 绑定用户空间里的已安装 Skill。
2. 已安装 Skill 有当前版本。
3. 用户主动更新已安装 Skill 后，绑定它的 Agent 后续使用新版。
4. 更新确认页必须展示受影响 Agent。
5. 系统 Skill 可直接绑定/选择，不要求先进入用户安装态；社区 Skill 绑定前必须先安装到 My Skills。
6. 运行时目录 scope 是实现细节，不能让 Agent 直接跟随 SkillHub public latest。
7. Agent 运行前必须生成 Runtime Manifest，作为 prompt、`skill_load`、sandbox allowlist 的共同授权真相。

这比“每个 Agent 单独固定版本”更符合普通用户心智，也比“跟随 SkillHub 最新版”更安全。

一个 Agent 可以绑定多个 Skill，但要有限制：

1. 第一版设置数量上限。
2. 如果多个 Skill 描述相似，提示可能冲突。
3. 对话页显示启用的 Skills。
4. 优先级设置不作为第一版主功能。

Skill 不可用时：

| 场景 | 产品行为 |
| --- | --- |
| Skill 已删除 | Agent 配置页显示“此 Skill 已不可用”，对话时不静默使用旧内容 |
| Skill 被下架 | 已安装版本可继续使用，但提示无法再获取更新 |
| Skill 内容校验失败 | 禁止绑定，并提示用户重新上传或联系发布者 |
| Skill 更新中用户正在对话 | 当前正在生成的回复不受影响；下一条消息按更新后的配置生效 |

Skill 版本变化不改写历史对话。若需要审计，可以记录当时使用的 Skill 名称和版本。

## 删除边界

如果用户删除一个已绑定 Skill：

1. 删除前展示受影响 Agent。
2. 用户确认后，Agent 自动解绑该 Skill。
3. Agent 配置页保留近期提示：“某 Skill 已被删除并解绑。”

如果是 SkillHub 下架，不应该自动删除用户已安装版本，除非安全原因。

## 发布边界

只有 Skill 所有者可以发布自己的 Skill。

用户不能：

1. 直接发布官方 Skill 的新版。
2. 直接发布别人社区 Skill 的新版。
3. 通过安装动作获得原 Skill 的发布权。

如果用户想修改并发布，必须先通过“下载”导出可编辑包并上传形成新的 Skill 身份。

发布失败时：

1. SkillHub 不出现新版本。
2. 旧公开版本保持不变。
3. 用户的私有版本仍然存在。
4. 用户可以重试发布。
5. 失败原因尽量可理解，但不暴露内部错误细节。

发布后继续编辑：

1. 编辑我的 Skill 后，已发布版本不能被原地改变。
2. 编辑我的 Skill 后，其他用户已安装版本不能被自动改变。
3. 删除我的本地草稿后，SkillHub 已发布版本不能消失。

## 下架、删除与禁用

需要区分：

| 动作 | 含义 |
| --- | --- |
| 删除我的 Skill | 从我的空间移除未发布或个人使用的 Skill |
| 下架 SkillHub 发布 | 新用户不能再安装，但已安装用户是否继续可用取决于安全策略 |
| 删除未发布版本 | 只删除私有草稿或从未发布的版本 |
| 禁用版本 | 平台因为安全原因阻止继续使用 |

第一版建议支持“下架”，谨慎支持“删除已发布版本”。

安全禁用是唯一可以打破“不自动影响用户”的例外，但必须可解释：

1. 平台可以禁用有风险版本。
2. 已安装用户打开 Agent 或 Skill 详情时看到明确提示。
3. 如果有安全新版，提示用户更新。
4. 如果没有可用新版，Agent 自动停用该 Skill，并告诉用户原因。

## 安装、更新与回滚

安装冲突：

1. 如果是同一个 Skill 的旧版本，提示“你已安装版本 1，可更新到版本 2”。
2. 如果是不同来源但同名，提示用户重命名或取消。
3. 不要静默覆盖用户已有 Skill。

更新冲突：

1. 用户基于已安装 Skill 创建自己的版本后，原 Skill 的更新不覆盖这个自定义版本。
2. 原安装仍可提示有新版。
3. 自定义 Skill 是新的 Skill 身份，独立迭代。
4. 第一版不做自动合并。

回滚：

1. 回滚可作为 P1，但模型要预留。
2. 已安装 Skill 需要保留可访问的历史安装版本。
3. 回滚也是用户主动动作。
4. 回滚前展示受影响 Agent。

## 下载（创建我的版本）

用户安装了社区 Skill 后，想改成适合自己的版本时，主动作叫“下载”。系统 Skill 本轮不提供这个动作。

内部语义可以叫 fork/create-my-version，但用户主按钮不使用长文案。

主流程：

1. 用户在社区 Skill 或已安装 Skill 详情页点击“下载”。
2. 平台导出带来源 claim 的可编辑包。
3. 用户修改后上传，平台创建一个新的“我的 Skill”。
4. 新 Skill 与原 Skill 保留来源关系。
5. 用户修改后生成自己的版本 1。
6. 用户可以自己使用，也可以作为新的社区 Skill 发布。

关键边界：

1. 新 Skill 不继承原 Skill 的发布权。
2. 新 Skill 的版本从版本 1 开始。
3. 新 Skill 的更新不影响原 Skill。
4. 原 Skill 的更新不自动合并到新 Skill。
5. 发布新 Skill 时，需要明确显示作者是当前用户，而不是原作者。

## 信任与隐私

社区 Skill 是用户生成内容，不能默认等同官方可信。

需要展示：

1. 作者。
2. 来源。
3. 更新时间。
4. 权限或能力摘要。
5. 风险提示。

发布确认页必须提醒用户：

1. 不要发布包含私人信息、密钥、内部资料的 Skill。
2. 发布后别人可以安装和使用。
3. 如果允许查看源内容，需要明确告诉用户。
