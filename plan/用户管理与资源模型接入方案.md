# 用户管理与资源模型接入方案

## 1. 文档角色说明

本文档是 DeerFlow 用户体系迁移的总方案主文档，回答的是“最终系统应该是什么样”。

它负责定义：

- 当前 DeerFlow 基线与问题边界
- 已锁定前提与长期稳定约束
- 认证主方案与登录保护原则
- 业务主真相与运行时主真相的映射
- 数据模型与表结构主定义
- Workspace / Skill / Knowledge Base / OSS 的主设计
- Gateway 与 frontend 的职责边界
- Legacy thread 接管原则

本文档不展开逐阶段任务清单。落地顺序以 `plan/DeerFlow用户管理执行方案.md` 为准。

## 2. 当前 DeerFlow 现状

### 2.1 Gateway 与前端现状

- Gateway 当前入口在 `backend/app/gateway/app.py`
- 已聚合 `threads / thread_runs / runs / agents / skills / memory / uploads` 等路由
- 当前没有统一认证中间层
- frontend 中 `frontend/src/server/better-auth/config.ts` 只是 email/password 占位实现，不能继续作为正式认证中心

### 2.2 运行时现状

- 当前主链路仍然是 LangGraph thread + Store + checkpointer
- `/api/threads/**` 是现有前端直接依赖的运行时主链路
- memory 仍是全局文件模型，不是用户级资源
- agents 仍落在 `.deer-flow/agents/*` 文件系统目录，不是用户级业务模型
- workspace 运行时目录仍然是 thread 级目录，而不是用户级 canonical workspace

## 3. 已锁定前提

- 根目录 `.env` 是单一配置源
- Gateway 启动时统一读取根目录 `.env`
- Gateway 是唯一认证真相
- 认证主入口统一在 Python Gateway
- Keycloak 当前按 `public client first` 跑通；若供应方要求 `PKCE`，则按供应方要求补齐
- DeerFlow v1 认证正式采用“Gateway + Keycloak + 浏览器 HttpOnly token cookie”模式
- 浏览器持有 `kc_access_token / kc_refresh_token / kc_id_token`，但前端 JavaScript 不直接读取这些 cookie
- 前端不得把 Keycloak token 持久化到 `localStorage / sessionStorage`
- `current_user` 的正式解析链路是：`kc_access_token -> Keycloak /userinfo`，失败后 `kc_refresh_token -> refresh -> /userinfo`
- `users` 保留为本地用户主映射表；DeerFlow v1 不再维护 `auth_sessions`
- 当前产品只有一个网页端，不做多端并发登录治理
- PostgreSQL 本轮先承接业务表，不强迁 LangGraph `checkpointer / store`
- `chats.thread_id` 直接作为产品会话主键，同时也是 LangGraph `thread_id`
- 不新增独立 `chat_id`
- 一个 chat 只能绑定一个 agent
- 不同 chat 可以绑定同一个 agent
- Workspace 最终产品目标仍是用户级正式资源，未来可见、可复用、可独立管理
- 当前阶段采用隐藏式 Workspace v1，不对用户露出
- Phase 1-3 不开放 Workspace 前端复用入口，但模型必须预留
- v1 每次新建 chat 默认自动创建一个新的 workspace 并绑定
- 用户重新打开某个 chat 时，继续使用该 chat 已绑定的 workspace
- Legacy thread 采用懒接管
- Knowledge Base 文件本体进入 OSS，但 `knowledge_base_files` 等 PG 业务表必须保留
- Skills 既要入库管理，又要同步到 OSS 顶级目录供 sandbox 使用

## 4. 认证主方案

### 4.1 目标链路

DeerFlow v1 的正式认证链路为：

`browser -> Python Gateway -> Keycloak -> Python Gateway callback -> 浏览器 HttpOnly kc_* cookie`

核心接口固定为：

- `GET /api/auth/login`
- `GET /api/auth/callback`
- `GET /api/auth/me`
- `POST /api/auth/logout`
- `POST /api/auth/refresh`

### 4.2 参考实现原则

协议参数和供应商要求以第三方 OAuth / Keycloak 文档为准；实际登录编排优先参考 `C:/Users/admin/Desktop/work/ecc_agent` 的已跑通实现。

重点参考文件：

- `C:/Users/admin/Desktop/work/ecc_agent/apps/ecc_agent/src/main.py`
- `C:/Users/admin/Desktop/work/ecc_agent/apps/ecc_agent/src/ecc_agent/auth_routes.py`
- `C:/Users/admin/Desktop/work/ecc_agent/apps/ecc_agent/src/ecc_agent/keycloak.py`
- `C:/Users/admin/Desktop/work/ecc_agent/apps/ecc_agent/src/ecc_agent/auth.py`
- `C:/Users/admin/Desktop/work/ecc_agent/apps/ecc_agent/src/ecc_agent/user_repository.py`

`ecc_agent` 的正式参考范围包括：

- `/login -> /callback -> /me -> /logout` 的路由编排
- 反向代理场景下 `x-forwarded-proto / x-forwarded-host / referer` 推导外部 origin 的方式
- `returnTo` 校验、`state` 承载跳转上下文、CSRF cookie 的处理方式
- `kc_*` cookie 的持有与重写
- `/me` 中“先 userinfo，再 refresh 恢复”的恢复链路
- 首次登录后本地用户 upsert 的时机

同时必须明确：

- `ecc_agent` 不提供 client 类型原样照搬依据
- 若供应方要求 `PKCE`，DeerFlow 仍需补齐，不因 `ecc_agent` 当前实现差异而放弃
- DeerFlow 普通业务接口不信任前端缓存用户态，权限判断仍由 Gateway 统一解析 `current_user`

### 4.3 Cookie 与安全边界

- `kc_access_token / kc_refresh_token / kc_id_token` 必须使用 `HttpOnly`
- `Secure` 在正式 HTTPS 环境中是必须项
- `SameSite` 必须显式配置，不能依赖默认行为
- 前端不得把 Keycloak token 存入 `localStorage / sessionStorage`
- middleware 可以继续用 cookie 存在性做轻量路由保护，但后端权限判断必须以 Gateway 的实时校验结果为准
- DeerFlow v1 不提供服务端强制踢会话、多端会话管理、会话审计能力

## 5. 登录保护原则

长期稳定保护面包括：

- `/api/auth/**`
- `/api/threads/**`
- `/api/runs/**`
- `/api/knowledge-bases/**`
- `/api/agents/**`
- `/api/skills/**`
- `/api/memory/**`
- `/api/threads/{thread_id}/uploads/**`
- `/api/threads/{thread_id}/artifacts/**`
- `/api/threads/{thread_id}/suggestions`
- `/workspace/**`

这里定义的是长期保护面，不等于一次性启用顺序。实际启用顺序、owner 校验打开时机、兼容层过渡策略，以执行总方案和阶段文档为准。

## 6. 业务主真相与运行时主真相映射

### 6.1 主真相分层

- `chats` 是产品会话主真相
- `chats.thread_id` 直接作为产品会话主键，同时也是 LangGraph `thread_id`
- checkpointer / Store 继续保存运行时状态，但不再承担唯一业务真相
- PostgreSQL 先承接业务主真相；运行时 `checkpointer / store` 继续保留兼容层职责

### 6.2 chat 绑定关系

- 一个 chat 最多绑定一个 agent
- 不同 chat 可以绑定同一个 agent
- chat 的 owner 一律来自服务端解析出的 `current_user`
- 前端不得传入 owner 字段决定归属
- v1 下每个新 chat 默认绑定一个新的隐藏 workspace，不向用户暴露跨 chat 复用入口

### 6.3 最终产品目标与当前阶段启用能力

最终产品目标是：

- Workspace 是用户级正式资源
- Workspace 未来可见、可复用、可独立管理
- 新建 chat 未来可选择已有 workspace；若未选择，再由后端自动创建

当前阶段启用能力是：

- Phase 1-3 暂不开放 Workspace 菜单、Workspace 列表和“新建 chat 选择已有 Workspace”入口
- v1 每次新建 chat 时由后端自动创建一个隐藏 workspace 并绑定
- 用户重新打开同一个 chat 时继续使用该 chat 已绑定的 workspace
- 当前阶段的隐藏式 Workspace 只是落地策略，不代表 Workspace 的最终产品定义

## 7. 数据模型与表结构主定义

最终业务主模型保留以下表：

- `users`
- `user_memories`
- `agents`
- `agent_skills`
- `agent_knowledge_bases`
- `skills`
- `knowledge_bases`
- `knowledge_base_files`
- `knowledge_chunks`
- `workspaces`
- `workspace_files`
- `chats`
- `messages`

### 7.1 users

- 存系统内用户主记录
- 第三方登录成功后在 Gateway 中 upsert

### 7.2 chats

- `thread_id uuid pk`
- `owner_user_id`
- `workspace_id nullable`
- `agent_id nullable`
- `title / status / created_at / updated_at`
- chat 只记录当前 `agent_id`
- 运行时每次执行都按当前 agent 配置、当前 skill 引用和当前 Knowledge Base 引用实时解析
- 若引用资源缺失、路径不可达或同步未完成，则忽略对应配置并继续执行模型
- 历史 chat 允许随 agent、skill、Knowledge Base 的当前状态变化而变化

### 7.3 messages

- 记录产品消息镜像
- 首批只覆盖新体系下的新会话
- 历史 thread 不做全量消息回填
- v1 只镜像用户可见消息，不把底层 tool 事件和 checkpoint 细粒度状态强行并入产品表

### 7.4 workspaces / workspace_files

- `workspaces` 是用户级 canonical workspace
- `workspace_files` 存文件元数据、路径、版本、状态

### 7.5 agents

- 从全局文件目录迁到“PG 业务记录 + 运行时生成配置”的模型
- 系统默认 agent 保持兼容

### 7.6 agent_skills / agent_knowledge_bases

- `agent_skills` 记录 agent 绑定的 skill 资源
- `agent_knowledge_bases` 记录 agent 绑定的 Knowledge Base 资源
- agent 绑定的是资源主记录
- chat 与 run 在执行时按当前资源引用实时解析，不再保存历史副本

### 7.7 skills

- system skills 继续兼容仓库级 skills 目录
- user skills 进入 PG 管理，并同步到 OSS / 运行时目录
- run 时按 agent 当前绑定实时加载 skill 内容
- skill 缺失、路径缺失或同步未完成时，忽略对应 skill 并继续执行模型

### 7.8 knowledge_bases / knowledge_base_files / knowledge_chunks

- Knowledge Base 文件本体只进 OSS
- PG 负责业务元数据、处理状态和索引关系
- `knowledge_chunks` 采用 `pgvector`
- run 时按 agent 当前绑定实时解析 Knowledge Base
- Knowledge Base 缺失、文件缺失或路径不可达时，忽略对应检索增强并继续执行模型

### 7.10 user_memories

- 最终替代当前全局 memory 文件模型
- 旧全局 memory 只作为 legacy 数据，不继续扩展

## 8. Workspace 与现有 thread 目录的映射

当前 DeerFlow 运行时只支持 thread 级目录：

- `threads/{thread_id}/user-data/workspace`
- `threads/{thread_id}/user-data/uploads`
- `threads/{thread_id}/user-data/outputs`

因此 `workspace` 不能直接等同于当前 thread workspace 目录，必须制度化区分主真相与运行时投影。

既定策略是：

- canonical workspace 是唯一业务主真相
- thread workspace 只是运行时投影目录，不承担长期业务主真相职责
- run 前固定执行 `canonical workspace -> thread workspace` 同步
- run 后固定执行 `thread workspace -> canonical workspace` 回写
- v1 冲突策略固定为“后写覆盖”，不做自动合并、不做双向冲突决策、不做用户提示式冲突管理
- 当前阶段不提供 Workspace 独立菜单、用户可见列表和“新建 chat 时选择已有 workspace”
- v1 每次新建 chat 时由后端自动创建新的隐藏 workspace 并绑定
- 数据模型必须继续保留用户级 workspace，为后续扩展到“可见可复用 workspace”预留空间

## 9. Skills / Knowledge Base / OSS 主设计

### 9.1 Skills

- system skills 继续兼容仓库级目录
- user skills 采用 PG 管理 + OSS 存包 + 运行时挂载
- Skills 是用户级资源，不再只是全局运行时目录

### 9.2 Knowledge Base

- Knowledge Base 是独立管理菜单，和 Agents 同级
- Workspace v1 暂不作为用户可见菜单
- 用户上传的原始文件进入 OSS
- PG 继续保留 `knowledge_base_files`

保留 `knowledge_base_files` 的原因：

- OSS 解决的是文件存储，不解决业务管理
- 需要在 PG 中保留文件列表、状态追踪、解析失败回显、去重和索引关系

### 9.3 OSS 顶级目录约束

- Knowledge Base 是 OSS 顶级目录资源
- Skills 同步到 OSS 顶级目录供 sandbox 使用
- Workspace 也应有独立的 canonical 存储前缀，不能把 thread runtime uploads 直接当作产品资源真相

## 10. Gateway 与 frontend 的职责边界

### 10.1 Gateway

- 统一承接 `/api/auth/**`
- 保留 `/api/threads/**`、`/api/runs/**` 作为运行时兼容层
- 新增 `/api/knowledge-bases/**`
- `/api/agents`、`/api/skills`、`/api/memory` 改造成用户感知接口
- `/api/threads/{thread_id}/uploads/**`、`/api/threads/{thread_id}/artifacts/**`、`/api/threads/{thread_id}/suggestions` 也纳入 `current_user + owner` 校验范围
- 所有 router 都需要补 `current_user` 解析、owner 校验和用户过滤

### 10.2 frontend

- frontend 当前 `better-auth` 仅为待退役占位实现
- 登录由 frontend 跳转 Gateway `/api/auth/login`
- 退出由 frontend 调 Gateway `/api/auth/logout`
- 登录态初始化以 Gateway `/api/auth/me` 为准
- `/workspace/**` 第一批纳入登录保护
- Workspace 在 v1 不作为用户可见菜单，不提供独立管理入口

## 11. Legacy thread 接管原则

- 旧 thread 采用懒接管
- 用户首次登录访问某个历史 thread 时，Gateway 补建 `chats` 归属记录
- 不做上线前全量回填
- 未被接管的匿名历史 thread 不纳入新用户隔离体系
- 某历史 thread 首次被成功懒接管后，`owner_user_id` 默认不可变
- 被接管 thread 一旦写入 `chats`，即视为进入新用户体系
- 懒接管不定义共享 owner 模式

## 12. 全局硬规则与验收原则

1. Gateway 是唯一认证真相。
2. Keycloak 是唯一登录态与失效真相。
3. 前端不得把 Keycloak token 持久化到 `localStorage / sessionStorage`。
4. DeerFlow v1 不维护 `auth_sessions` 作为正式认证模型。
5. `current_user` 由 Gateway 基于 `kc_*` cookie 与 Keycloak 校验结果统一解析。
6. `chats.thread_id` = 产品 chat 主键 = LangGraph `thread_id`。
7. chat 与 run 按当前 agent、skill、Knowledge Base 引用实时解析资源。
8. 历史 chat 允许随 agent、skill、Knowledge Base 当前状态变化而变化。
9. canonical workspace 是主真相，thread workspace 只是运行时投影。
10. Phase 1-3 不开放 Workspace 前端复用入口，但模型必须预留最终可见、可复用、可独立管理能力。
11. `ecc_agent` 不仅参考认证流程，也正式参考其 HttpOnly token cookie 模型；若供应方要求 `PKCE`，DeerFlow 仍需补齐。
12. 所有 owner 归属都必须由服务端 `current_user` 写入。
13. LangGraph `checkpointer / store` 本轮不强迁入 PG，只保留运行时职责。
14. 阶段验证失败必须立即中断，不允许继续推进下一阶段。

全局验收时至少还要确认：

- 认证主入口仍然只在 Python Gateway
- KB 文件本体在 OSS，业务元数据和状态仍保留在 PG
- Workspace 继续采用 canonical workspace + thread workspace 映射模型

## 13. 迁移路线总览

- 先完成 Auth、`.env` 单一来源、PG `users` 与 `current_user`
- 再落 `chats / messages / thread owner`
- 然后落隐藏式 `workspaces + threads 主链绑定 + workspace 映射`
- 接着完成 `agents + 实时资源关联`
- 再推进 `skills` 业务化与实时同步
- 再推进 `knowledge base` 资源层、索引层和运行时接入
- 最后完成 `user_memories` 替换与 legacy 清理
